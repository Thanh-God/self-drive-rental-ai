# Local Qwen and location routing

Qwen runs through Ollama at `http://127.0.0.1:11434/api/chat`, model configurable with `QWEN_MODEL` (default `qwen3:8b`; allowlist `qwen3:8b`, `qwen3:4b`). Enable only with `QWEN_PARSER_ENABLED=true`; leave `GEMINI_PARSER_ENABLED=false`. Both default off. No API key or cloud call is required by the Qwen adapter. Qwen is an extraction model, not an authority for price, availability, identity or route facts. Name resolution and confirmation must precede booking actions. USER text extraction endpoint and review flow are documented in [the assistant contract](ai-assistant.md).

Requests use JSON Schema, `think=false`, `stream=false`, context4096 and output512tokens. Input is at most1000characters; clients should omit personal identifiers; the endpoint rejects common identifier patterns, not every form of personal data. Local HTTP responses are byte bounded with whole-call deadlines; malformed output is rejected. No transcript is persisted. One inference per backend instance is admitted; excess requests receive429 without queuing. The adapter never pulls a model automatically. Keep-alive is2minutes; the full-call deadline is60seconds, and the frontend request timeout65seconds.

`GET /api/v1/ai/locations` requires USER and exposes only ACTIVE catalog IDs, names, categories, coordinates and optional curated visit metadata. Legacy metadata is unknown; it does not imply24-hour access. ADMIN maintains weekly schedules, date exceptions, estimated visit duration and source evidence under [the visit metadata contract](location-visit-metadata.md). There is no popularity/trending feed.

`POST /api/v1/ai/routes/preview` accepts `{ "locationIds": ["id-a", "id-b"] }`, 2–8 distinct active IDs. `AI_ROUTING_ENABLED` defaults false. Coordinates are resolved server-side; request URLs and arbitrary coordinates are never forwarded. The local OSRM service is fixed at `127.0.0.1:5000`. Response status is VERIFIED, NO_ROUTE or UNAVAILABLE; unsuccessful results have null distance/time. VERIFIED means a graph route was returned, not a guarantee of road accessibility or live traffic. Distances are meters and durations seconds. Snapping is limited to1000meters per waypoint. Preview does not save itineraries or alter bookings. Each backend instance admits at most two simultaneous OSRM calls; excess requests receive429. There is no response cache, retry or provider fallback.

OSRM preparation follows the official MLD pipeline: `osrm-extract -p /opt/car.lua`, `osrm-partition`, `osrm-customize`, then `osrm-routed --algorithm mld`. Keep PBF source URL/date/hash, image digest, generated graph and build logs together. Bind only loopback. Do not overwrite existing graph or stop someone else's service. Before preparing Vietnam data, check available disk/RAM and set bounded CPU/memory limits. OpenStreetMap attribution and ODbL obligations apply; OSRM does not itself supply basemap tiles or weekly tourism trends.

Sources: [Ollama model](https://ollama.com/library/qwen3:4b), [structured output](https://docs.ollama.com/capabilities/structured-outputs), [OSRM](https://github.com/Project-OSRM/osrm-backend), [Vietnam extract](https://download.geofabrik.de/asia/vietnam.html).

For a running local graph, execute `python scripts/coordination/ai3/probe-osrm.py --evidence .runtime/<new-probe-directory>`. The read-only probe checks a Da Nang–Hoi An driving route and an off-network coordinate; it exits nonzero on failed assertions. It does not accept remote hosts, start services or mutate business data. A graph extracted for one region does not imply national coverage; preserve its bounding box together with the source PBF hash. This probe validates the raw OSRM graph, separately from backend HTTP/API and browser acceptance.

For authenticated HTTP routing verification, first run Java21 `mvnw verify` on an isolated backend copy. The ordinary suite does not require a running OSRM service: online/offline integration methods require explicit `KDRIVE_ROUTING_MODE=online` or `offline`, respectively, and conditional skips are not graph verification. Do not set these modes for ordinary verification.

Run `python scripts/coordination/ai3/run-routing-proof.py --backend-root .runtime/<verified-backend-copy> --evidence .runtime/<new-proof> --reuse-evidence .runtime/<previous-native-evidence> --graph-dir .runtime/<regional-graph-directory> --graph-manifest .runtime/<graph-manifest.json>` for the full local proof. It checks graph hashes and the pinned image, refuses an occupied port5000, starts only its own read-only graph container, and reuses the exact stopped guarded MySQL fixture at33676. Online and offline use separate marked schemas and no skipped tests; both include HTTP authorization, input validation and per-request record invariance. Deliberately requesting each mode in the opposite provider state must fail with the expected assertion. The script keeps its OSRM container stopped and preserves graph/fixture volumes and evidence. It does not activate the application's main services or provide national coverage.

The underlying guarded MySQL runner requires `--routing-mode online|offline` when selecting `LocationRouteHttpServerTest`; mode/provider mismatch is rejected before creating evidence or starting MySQL. Other suites need no routing mode. Routing snapshots include existing location/category records, booking/history and itinerary/day/item records; intentional update probes verify that unchanged row counts cannot conceal modifications.
