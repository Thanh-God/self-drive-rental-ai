# Local Qwen and location routing

Qwen runs through Ollama at `http://127.0.0.1:11434/api/chat`, model configurable with `QWEN_MODEL` (default `qwen3:8b`; allowlist `qwen3:8b`, `qwen3:4b`). Enable only with `QWEN_PARSER_ENABLED=true`; leave `GEMINI_PARSER_ENABLED=false`. Both default off. No API key or cloud call is required by the Qwen adapter. Qwen is an extraction model, not an authority for price, availability, identity or route facts. Name resolution and confirmation must precede booking actions. USER text extraction endpoint and review flow are documented in [the assistant contract](ai-assistant.md).

Requests use JSON Schema, `think=false`, `stream=false`, context4096 and output512tokens. Input is at most1000characters; clients should omit personal identifiers; the endpoint rejects common identifier patterns, not every form of personal data. Local HTTP responses are byte bounded with whole-call deadlines; malformed output is rejected. No transcript is persisted. The criteria parser and itinerary sequence planner each have their own one-inference semaphore; excess requests to the same component receive429 without queuing. There is no shared inference limit across both components. The adapter never pulls a model automatically. Keep-alive is2minutes; each Qwen HTTP call has a60second deadline, and the frontend parse/preview request timeout is65seconds. Itinerary preview and save also call OSRM; the Qwen deadline is not a deadline for the entire business request.

`GET /api/v1/ai/locations` requires USER and exposes only ACTIVE catalog IDs, names, categories, coordinates and optional curated visit metadata. Legacy metadata is unknown; it does not imply24-hour access. ADMIN maintains weekly schedules, date exceptions, estimated visit duration and source evidence under [the visit metadata contract](location-visit-metadata.md). There is no popularity/trending feed.

`POST /api/v1/ai/routes/preview` accepts `{ "locationIds": ["id-a", "id-b"] }`, 2–8 distinct active IDs. `AI_ROUTING_ENABLED` defaults false and gates this route-preview endpoint. Coordinates are resolved server-side; request URLs and arbitrary coordinates are never forwarded. The local OSRM service is fixed at `127.0.0.1:5000`. Response status is VERIFIED, NO_ROUTE or UNAVAILABLE; unsuccessful results have null distance/time. VERIFIED means a graph route was returned, not a guarantee of road accessibility or live traffic. Distances are meters and durations seconds. Snapping is limited to1000meters per waypoint. Preview does not save itineraries or alter bookings. The route-preview service admits at most two simultaneous provider calls; excess requests receive429. Itinerary preview/save use the OSRM client directly and do not share that semaphore or feature flag. Each OSRM HTTP call has a5second deadline. There is no response cache, automatic retry or provider fallback; itinerary validation can request individual legs when a route response lacks leg details.

OSRM preparation follows the official MLD pipeline: `osrm-extract -p /opt/car.lua`, `osrm-partition`, `osrm-customize`, then `osrm-routed --algorithm mld`. Keep PBF source URL/date/hash, image digest, generated graph and build logs together. Bind only loopback. Do not overwrite existing graph or stop someone else's service. Before preparing Vietnam data, check available disk/RAM and set bounded CPU/memory limits. OpenStreetMap attribution and ODbL obligations apply; OSRM does not itself supply basemap tiles or weekly tourism trends.

Sources: [Ollama model](https://ollama.com/library/qwen3:4b), [structured output](https://docs.ollama.com/capabilities/structured-outputs), [OSRM](https://github.com/Project-OSRM/osrm-backend), [Vietnam extract](https://download.geofabrik.de/asia/vietnam.html).

For a running local graph, execute `python scripts/coordination/ai3/probe-osrm.py --evidence .runtime/<new-probe-directory>`. The read-only probe checks a Da Nang–Hoi An driving route and an off-network coordinate; it exits nonzero on failed assertions. It does not accept remote hosts, start services or mutate business data. A graph extracted for one region does not imply national coverage; preserve its bounding box together with the source PBF hash. This probe validates the raw OSRM graph, separately from backend HTTP/API and browser acceptance.

For authenticated HTTP routing verification, first run Java21 `mvnw verify` on an isolated backend copy. The ordinary suite does not require a running OSRM service: online/offline integration methods require explicit `KDRIVE_ROUTING_MODE=online` or `offline`, respectively, and conditional skips are not graph verification. Do not set these modes for ordinary verification.

For the full local proof, first read the [fixture policy](../../skills/kltn-docker-fixtures/SKILL.md) and the [current native runner guide](../../scripts/coordination/c14-core/README.md). The default pools are pinned in local registries `.runtime/docker-fixtures/osrm.json` and `.runtime/docker-fixtures/mysql-core.json`. Check the registered identity/image/mount/marker and stopped state; missing registries or drift are blockers, not permission to create replacements. Do not stop a provider or fixture started by someone else.

Run from the repository root: `python scripts/coordination/ai3/run-routing-proof.py --backend-root .runtime/<verified-backend-copy> --evidence .runtime/<new-proof> --reuse-evidence .runtime/<verified-native-evidence> --osrm-registry .runtime/docker-fixtures/osrm.json --graph-dir .runtime/<registered-regional-graph-directory> --graph-manifest .runtime/<graph-manifest.json>`. Replace placeholders with verified local paths; this is not an instruction to create a new fixture. The runner checks graph hashes, the pinned image and exact registered OSRM identity/mount, refuses an occupied port5000, and starts the stopped registered test container. It delegates MySQL checks to `scripts/coordination/c14-core/run-mysql.py`, reusing the exact stopped fixture identified by native evidence at33676. Both pools are used sequentially, with separate marked schemas for online/offline tests.

Online and offline require no skipped tests; both include HTTP authorization, input validation and per-request record invariance. Deliberately requesting each mode in the opposite provider state must fail with the expected assertion. The runner stops the OSRM fixture it started and preserves graph/fixture volumes, schemas and evidence. It does not activate the application's main services or provide national coverage. A new container requires a separately approved isolation reason and `--new-fixture-reason`; that flag does not itself grant permission. Legacy creation flows are only for explicitly scoped historical replay. Never direct write tests at33385/3306, mount the application database volume or delete accumulated schemas/volumes without the applicable retention approval.

The underlying guarded MySQL runner requires `--routing-mode online|offline` when selecting `LocationRouteHttpServerTest`; mode/provider mismatch is rejected before creating evidence or starting MySQL. Other suites need no routing mode. Routing snapshots include existing location/category records, booking/history and itinerary/day/item records; intentional update probes verify that unchanged row counts cannot conceal modifications.
