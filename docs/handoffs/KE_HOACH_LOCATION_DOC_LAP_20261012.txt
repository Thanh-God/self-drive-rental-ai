4. HIỆN TRẠNG ĐÃ KIỂM TRA

Database đã có:
  location_categories: id VARCHAR(36), name VARCHAR(100) UNIQUE NOT NULL.
  locations: id VARCHAR(36), category_id, name VARCHAR(200),
             latitude DECIMAL(10,7), longitude DECIMAL(10,7), status VARCHAR(10).
  latitude có CHECK [-90,90]; longitude có CHECK [-180,180].
  category_id là FK; itinerary_items.location_id cũng tham chiếu locations.

Module location chưa có API/controller/service/entity hoàn chỉnh trong baseline đã đọc. Frontend admin LocationsPage đang dùng ManagementScreen collection=locations ở chế độ demo. Route /admin/locations chưa có màn hình API riêng. Demo và dữ liệu MySQL không phải cùng nguồn.

Demo location dùng ACTIVE/INACTIVE và trường lat/lng; API mới nên dùng latitude/longitude rõ nghĩa rồi map ở UI riêng. Không đổi toàn bộ demo data model để khớp API. Mục tiêu là API mode dùng MySQL thật, lỗi API hiện đúng trạng thái lỗi, không thay bằng demo.

Các bảng location đã có nên KHÔNG tạo bảng mới hoặc schema.sql. Không sửa V1/V2 đã áp dụng, không clean/repair/baseline thủ công. Không thay đổi bảng itinerary để triển khai AI. Nếu schema thực tế thiếu hoặc validation thất bại, giữ evidence và báo blocker trước sửa migration.

7. HỢP ĐỒNG API DỰ KIẾN — CHỐT TRONG PLAN TRƯỚC CODE

Chỉ namespace /api/v1/admin/... để giữ quyền ADMIN hiện hành. Không tự công khai
GET location cho Guest/User vì đó là contract riêng có thể liên quan AI sau này.
Các endpoint dự kiến:
  GET  /api/v1/admin/location-categories
  POST /api/v1/admin/location-categories
  PUT  /api/v1/admin/location-categories/{id}
  GET  /api/v1/admin/locations
  GET  /api/v1/admin/locations/{id}
  POST /api/v1/admin/locations
  PUT  /api/v1/admin/locations/{id}
Không thêm DELETE.

Category body: name. Category view: id, name.
Location body: categoryId, name, latitude, longitude, status.
Location view: id, categoryId, categoryName, name, latitude, longitude, status.
ACTIVE/INACTIVE được validate explicit phía server; không nhận chuỗi tùy ý.
Đọc Admin thấy cả ACTIVE và INACTIVE, không giả INACTIVE là đã xóa.

Status HTTP: ghi rõ trong plan/test trước code: tạo201, đọc/cập nhật200,
input sai400, category/location không tồn tại404, unique/conflict409,
không đăng nhập401, USER/STAFF403. Dùng conventions của DomainException,
không trả HTTP200 kèm success=false cho lỗi.

Tọa độ: BigDecimal/validation phù hợp DECIMAL(10,7), không dùng chuỗi không kiểm
hoặc NaN/Infinity. Chốt và test cách xử lý quá7 chữ số thập phân trước code:
ưu tiên từ chối400 thay vì âm thầm làm tròn. Điểm0,0 hợp lệ; giới hạn90/-90,
180/-180 hợp lệ; vượt giới hạn bị từ chối và không có row mới/thay đổi.
Name category100/location200; không blank sau trim, không SQL injection.
FK category được service kiểm tra, lỗi ràng buộc không biến thành500.

Locations hiện không có cột version. Không tự thêm migration chỉ để sao chép
pattern module khác. Trong plan đề xuất cơ chế chống form cũ không đổi schema
(ví dụ expected snapshot/revision digest + conditional update/row lock);
review rõ contract request/response và cần test stale409. Không dùng timestamp
client hoặc hash so với chính payload mới làm bằng chứng. Nếu chưa có cách
nhất quán, báo checkpoint kỹ thuật và trao đổi với người điều phối; không
đánh dấu chống lost update PASS hoặc ghi đè im lặng. Đây là quyết định kỹ thuật,
không phải quyền xóa dữ liệu hay phê duyệt chính sách nghiệp vụ mới.

8. CÁCH CHỨC NĂNG HOẠT ĐỘNG

Admin đăng nhập → vào /admin/locations → React gọi API category/location.
Backend xác minh JWT và role ADMIN → DTO validate → service transaction →
repository ghi/đọc MySQL → trả DTO → UI reload/hiển thị dữ liệu vừa đọc.

Tạo category trước, nhận ID thật, chọn category cho location. Tên hiển thị được
map từ dữ liệu backend, không hardcode ID/name của seed/demo. Khi tạo thành công,
form reset hợp lý và danh sách đọc lại từ server; refresh trang vẫn thấy row.
Nếu tạo/cập nhật lỗi, giữ dữ liệu form để sửa, hiện domain message và không báo
thành công. Trong pending, chặn POST/PUT trùng bằng guard đồng bộ, không chỉ CSS.

Khi edit: load bản hiện tại/revision, submit đúng ID, server kiểm bản cũ và quyền,
UI đọc lại state mới. Nếu409, không ghi đè; cho tải lại dữ liệu mới rồi sửa tiếp.
Không cập nhật danh sách bằng cách giả success trước khi request thành công.
Lỗi GET hiện thông báo và retry; chỉ show empty khi GET thành công trả [];
không fallback sang demo khi API mất kết nối.

INACTIVE: row vẫn có ID/category/tọa độ và xuất hiện đúng trạng thái trong trang
Admin. Các tham chiếu itinerary/snapshot cũ giữ nguyên. Chưa có logic Map/AI
được nghiệm thu nên không vẽ map hoặc tạo route estimates giả để tuyên bố hoàn tất.

- Anonymous401, USER403, STAFF403 cho tất cả endpoint Admin; ADMIN hợp lệ.
- Category create/list/update readback; name blank/too-long/normalizedduplicate;
 409 unique có đúng1 row, không500 hoặc phát sinh thêm row.
- Location create/detail/list/update đúng ID và categoryName, tồn tại saurestart.
- Category thiếu/không tồn tại, locationID lạ, name blank/too-long, nullcoordinate,
 tọa độ ngoài range, quá precision, status tùy ý: lỗi rõ và DB không đổi.
- Boundary coordinates và0,0; không ép0 thành empty bằng truthy checks.
- Đổi category cập nhật đúng một location, category khác giữ nguyên.
- Đổi ACTIVE/INACTIVE giữ ID/row/FK, không đổi booking/branch/vehicle/itinerary.
- Nếu stale update contract có revision: hai client load cùng bản, A update,
 B bị409, sourceDB giữ dữ liệuA, không thêm audit giả; freshreload mới choB.
- Không có DELETE phá FK/itinerary; seed reference đại diện kiểm FK còn nguyên.
- Query exact data before/after; đếm số row đơn thuần không đủ chứng minh update.
- Native command/SQL error phải nonzero, không cast empty thành0/PASS.

Frontend:
- Mount component thật, form required/boundary/validation; API error message,
 list loading/empty/error/retry; không coi adapter mock là backendPASS.
- Hold response POST/PUT thật sau route.fetch; exactly1request/1write trongpending,
 button disabled, guard release sau lỗi, không false success.
- Realbrowser Admin tạo/edit/status/category, reload persistence + SQL readback.
- USER/STAFF directURL không thấy dữ liệu Admin; forgedAPI request bị từ chối.
- Stale409 hiển thị và không overwrite; exact active/inactive state.
- Category/location lựa chọn là ID thật; không lấy lat/lng demo khi API thất bại.
- Console/pageerrors bất ngờ phải FAIL. Lỗi HTTP âm chỉ được phân loại với exact
 endpoint/method/status, không bỏ qua mọi4xx/500 hoặc mọi URL chứalocations.
- Ảnh loading/error/form/pending/list/readback cần có expected/actual assertions,
 screenshot đơn lẻ hoặc health200 không chứng minh cảluồng PASS.

Gates:
  backend (JDK21): ./mvnw.cmd verify trênWindows, ./mvnw verify trênUnix.
  frontend: npm test -- --test-concurrency=1; npm run lint; npm run build demo/API.
  MySQL integration bắt buộc của location phải thực sự execute0skip.

  Sau sửa source cuối, chỉ rerun các kiểm tra bị tác động và requiredgates;
  không kết luận từ một lần test trước đó nếu hash/dependency đã đổi.

12. GIT COMMIT VÀ UPDATE KHI HOÀN THÀNH

Sau mỗi checkpoint/thay đổi source/test/docs hoàn tất, commit tương ứng. Nếu bị
ngắt/blocked, vẫn commit phần có ích như WIP rõ ràng; chưa bàn giao như DONE.
Không gom nhiều tuần thay đổi thành một commit và không tự amend commit cũ.
Stage rõ file/hunk thuộc lượt, không git add --all để kéo secrets/build vào Git.

Ví dụ tên commit (không tên agent):
  feat(location): add admin category API [PARTIAL]
  feat(location): validate catalog persistence [VERIFIED scoped]
  feat(location): add API management screen [VERIFIED scoped]
  test(location): cover permission and stale updates [VERIFIED scoped]
  docs(location): record final handoff [VERIFIED scoped]

Trước mỗi commit:
  git status --short
  git diff --check
  git diff --cached --stat
  git diff --cached
Chỉ commit secrets-placeholder hợp lệ, không secret thật, .env/test.env/privatejson,
DB dump/volume, dependency/cache, target/dist hoặc screenshots/runtime logs.
Tài liệu result không được lộ JWT/password, kể cả accountfixture.

Lệnh push khi checkpoint cần sao lưu hoặc khi hoàn thành:
  git push -u origin feature/location-catalog-20261012
Những lần sau:
  git push origin feature/location-catalog-20261012
Không force push. Nếu bị từ chối do lịch sửremote khác, fetch/read diff và báo
người điều phối, không reset/rewrite để đẩy bằng mọi giá.

Khi tự đánh giá DONE, required tests/lint/build/acceptance của lượt phải PASS
trên source cuối. Sau đó push branch, gửi URLbranch + commitSHA + resultfile +
evidence bundle cho người điều phối. Mở PR từ feature/location-catalog-20261012
vào update-20261012-0920 khi chủ project yêu cầu/đồng ý luồng PR. Không chọn
master mặc định, không merge PR của mình hoặc xóa branch tự động.

Người điều phối sẽ kiểm source/hash, chạy decisive checks, nhận diện conflict
với C8 và chốt phần nối AppRoutes. Nếu nhánh tích hợp đã có C8 mới, reviewer sẽ
chọn thời điểm merge; bạn không tự pull/merge C8 vào nhánh làm việc đang test
rồi tiếp tục dùng evidence/JAR cũ. Nếu có cập nhật baseline, test lại phần
bị tác động và ghi audit khác biệt.

13. BÀN GIAO VÀ EVIDENCE PHẢI GỬI

Trên máy mới tạo .runtime/coordination-location-<timestamp>/TASK.md và evidence
riêng. TASK lấy kế hoạch này, thêm baseline/môi trường/paths/commands cụ thể.
HANDOFF.md chỉ tạo khi có kết quả; Codex A tạo ACCEPTANCE riêng sau nghiệm thu.
Bản result versioned ở docs/handoffs/location-catalog-result.md tham chiếu
artifact private bằng tên/path/hash, không chứa secrets hoặc bản DB.

HANDOFF tối thiểu:
- Người thực hiện, branch, HEAD/status đầu-cuối và commitSHA từngcheckpoint.
- File thay đổi cả NEW/untracked, hash trước/sau; phầnintegration routehunk.
- Perrequirement DONE/PARTIAL/BLOCKED/NOTVERIFIED, không dùng tỷ lệ ước lượng.
- Command đầy đủ/workingdir/toolversion/exit, sốtest pass/fail/skip và XML/log.
- Payload/HTTPstatus redacted, assertions UI/SQLexpectedactual trước/sau.
- APIcontract mới/changed, schema/hash/Flywaystate và JARmanifest.
- Knownlimits/deletepolicy/stalecontract, phầnchưađạt và cách táichạy.
- PID/container/volume/port do mình tạo, stop/readback và danh sáchKEEP.
- Không tự sửa bàn giao người trước, không hardcode flagsPASS.

Gửi evidence qua kênh chia sẻ do chủ project chọn. Nếu nénbundle, loại toàn bộ
.env/privatecredentials/DB riêng tư trước; tạoSHA256 của bundle và manifest
để đối chiếu. Không đẩy evidence nhạy cảm vào GitHub public. Screenshot/log
không có secrets có thể gửi riêng; thiếuartifact thì reviewer ghiNOTVERIFIED,
không tự nhận là nghiệmthuPASS vì remotecommit tồn tại.
